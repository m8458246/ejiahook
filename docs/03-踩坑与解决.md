## 1. 配置读不到：`Unknown authority`

**现象**：模块日志显示 hook 都装好了，但行为完全没变。logcat 里：

```
E ActivityThread: Failed to find provider info for com.cycy.ejiahook.config
W EjiaHook: 读取模块配置失败: java.lang.IllegalArgumentException: Unknown authority com.cycy.ejiahook.config
```

**定位**：模块 App 声明了导出 Provider，shell 里 `content call` 能正常返回，但目标进程里调用失败。
排查过：Provider 注册正常（`dumpsys package` 能看到）、目标 targetSdk 29（不受包可见性限制）、
模块 App 进程当时也活着。怀疑与 ColorOS 的应用冻结 / 系统对跨应用 Provider 的额外限制有关。

**解法**：放弃 Provider 作为主通道，改成**共享存储文件**（模块 App 用 MediaStore 写，
目标进程直接读文件），Provider 只作兜底。改完立刻生效。

**教训**：跨进程传配置，文件比 Binder 稳。

---

## 2. 框架 remote prefs 返回空

**现象**：`getFrameworkProperties()` 里 `PROP_CAP_REMOTE` 是 true，但
`getRemotePreferences("config")` 返回的 `getAll()` 是空 map。

**定位**：反编译 LSPosed 的 `framework.dex` 确认实现是通过 Binder 找 daemon 要一份快照，
daemon 那边没给出来（可能和模块 App 的 prefs 状态/时序有关）。没继续深挖。

**解法**：同样退回文件通道。

**教训**：框架给的"能力位"只代表接口存在，不代表数据一定拿得到，必须有兜底。

---

## 3. 包可见性：点按钮提示"没找到应用"

**现象**：模块里点「获取真实定位」弹"没找到神州e家"，但手动打开 App 一切正常。

**定位**：模块 App `targetSdk=34`，Android 11+ 有包可见性限制，没声明 `<queries>` 时
`getLaunchIntentForPackage("com.dcits.ehome")` 直接返回 null。

**解法**：

```xml
<queries>
    <package android:name="com.dcits.ehome" />
</queries>
```

再加一层兜底：拿不到 launch intent 就用显式组件拉起

```java
intent.setComponent(new ComponentName("com.dcits.ehome",
        "com.dcits.ehome.activity.SplashScreenActivity"));
```

**教训**：Android 11+ 只要涉及"查询别的应用"，先想 `<queries>`。
另外这不影响反向：目标应用不需要"看得见"模块，显式广播/拉起都不受限制。

## 4. CI 每次签名不同，装不上

**现象**：

```
Failure [INSTALL_FAILED_UPDATE_INCOMPATIBLE: Existing package ... signatures do not match]
```

**定位**：release 用了 `signingConfig = signingConfigs["debug"]`，而 debug keystore 是
GitHub runner 每次新生成的，两次构建签名必然不同。

**解法**：仓库里放一个固定 keystore，debug/release 都用它签：

```kotlin
signingConfigs {
    create("stable") {
        storeFile = file("keystore.jks")
        storePassword = "..."
        keyAlias = "..."
        keyPassword = "..."
    }
}
```

**教训**：更麻烦的是**卸载重装的副作用**——LSPosed 的启用状态和作用域会一起被清掉，
用户得重新勾选。所以签名一定要固定，别图省事用 debug 默认签名。

## 5. 下载到的是旧包

**现象**：CI 明明构建成功了，下载的 APK 却还是上一版（文件大小、dex 内容都对不上）。

**定位**：GitHub Release 资产的 CDN 缓存，短时间内重复下载会命中旧缓存。

**解法**：下载 URL 加个时间戳破缓存：

```bash
curl -sL -o app.apk "https://github.com/u/r/releases/download/latest/app-release.apk?ts=$(date +%s)"
```

**教训**：验证"装的是不是新包"最可靠的办法是比对文件大小 / 在 dex 里 grep 一个新加的方法名。

---

## 6. 配置写进 `xxx (1).json`

**现象**：App 里改了配置，模块读到的还是旧值；`/sdcard/Download` 下出现
`ejiahook (1).json`、`ejiahook (2).json`… 一堆文件。

**定位**：MediaStore 插入同名文件不会覆盖，而是自动改名。而查询时按
`_display_name` 只查到自己创建的条目，看不到 root 手工创建的那个文件，于是每次都 insert。

**解法**：

- 写之前先按 `_display_name` + `relative_path` 查已有条目，有就 `openOutputStream(uri, "wt")` 覆盖
- 模块侧读取时按修改时间取最新的一个（兼容历史遗留的带编号文件）
- 最终收敛成一份：App 创建过一次之后，后续都在原地更新

**教训**：MediaStore 不是普通文件系统，`DISPLAY_NAME` 不保证唯一，`RELATIVE_PATH` 才是定位依据。

---

## 7. 写配置写回了旧路径

**现象**：明明改了 `RELATIVE_PATH` 到 `Download/ejiahook/`，结果旧文件
`Download/ejiahook.json` 又被更新了。

**定位**：查询逻辑里留了"找不到就用任意同名文件"的兜底，写路径复用了这个查询，
于是找到了旧文件并覆盖它。

**解法**：读和写分开——写只认目标目录（`findIdInSubdir`），找不到就 insert 新文件；
读才允许回退到旧位置。

**教训**：读的容错逻辑不要复用到写上。

---

## 8. 改坐标但地址不变

**现象**：坐标改到 134 公里外，考勤页显示"无法打卡、距离 134186 米"，
但地址栏还是本地地址。

**定位**：不是 bug。百度 SDK 在交出 `BDLocation` 之前，已经按**真实位置**做了逆地理编码，
地址字段和经纬度字段是两套独立数据。我们只改了经纬度数字。

**解法**：把地址各段（省/市/区/街道/完整地址）也做成可覆盖。

**教训**：改定位 ≠ 改地址。要地址一致，要么手填覆盖，要么从源头伪造（改 WiFi/基站，
让 SDK 自己算错）——后者工作量大得多。

---

## 9. 改了"完整地址"页面没反应

**现象**：填了完整地址，考勤页那行字纹丝不动。

**定位**：H5 拿地址有两条路——Cordova 插件读 `d()`（完整地址），dsbridge 读
`c0()+i()+r()+k0()`（省市区街道拼）。考勤页走的是后者。

**解法**：把 `d()` 改成由"省+市+区+街道+详细地址"自动拼，这样两条路共用一份输入，
不会再出现"改这里、它从那里取"。

**教训**：同一个语义在代码里可能有多套读取方式，先确认页面到底读哪个，再决定改哪。

---

## 10. 日志和实际值"对不上"

**现象**：日志 `25.064568,102.702976`，H5 收到 `25.064567743355376,102.70297566702634`。

**定位**：日志用 `%.6f` 打印，四舍五入到 6 位小数，差约 3 厘米。

**解法**：改用 `Double.toString()`，和 JSON 里的写法完全一致，可以逐字比对。

**教训**：用来做核对的数据，打印精度要和对端一致，否则会制造假问题。

---

## 11. 方法名找不到（混淆）

**现象**：想 hook `getLatitude()`，`getDeclaredMethod` 直接抛 `NoSuchMethodException`。

**定位**：目标 APK 把百度 SDK 混淆了，实际方法是 `K()/Q()`。

**解法**：从调用点反推——在 jadx 里搜谁在用 `BDLocation`，看它调了哪些方法；
再用 SDK 解析服务端 JSON 的代码确认字段语义（`province→c0`、`city→i`、`district→r`、`street→k0`）。
详见 `05-逆向速查.md`。

**教训**：不要按官方 API 名字猜，一定要从 APK 里读出来。所有按名字找方法的 hook 都要
`try/catch` 并打日志，找不到时降级而不是崩溃。

---

## 12. 卸载重装后模块失效

**现象**：`pm uninstall` + 重装后，LSPosed 里模块变回未启用，作用域也没了。

**定位**：LSPosed 把启用状态/作用域存在 `modules_config.db`，键是包名，卸载时被级联删除。

**解法**：避免卸载——固定签名，用 `pm install -r` 覆盖安装。

**教训**：调试期频繁卸载重装，会让"模块是否启用"这个变量反复变化，排查问题时容易误判。

---

## 13. 应用突然写不了自己的数据目录

**现象**：模块 App 保存配置失败，`shared_prefs` 目录建不出来。

**定位**：之前手工在 `/data/data/<pkg>` 下建过目录，`chown` 命令因为变量为空执行失败，
目录留在 `root:root 755`，应用（uid 10xxx）没有写权限。

**解法**：`chown <uid>:<uid>` + `chmod 771`，必要时 `restorecon`。

**教训**：root 下动 `/data/data` 很容易留下错误属主。要么别动，要么改完立刻核对 `stat`。

---

## 14. 截图全黑、无障碍树为空

**现象**：目标 App 的 WebView 页面截出来是纯黑，`observe_screen` 返回 `no_window`。

**定位**：X5 WebView 用了安全窗口（FLAG_SECURE 类），截图和无障碍都拿不到内容。

**解法**：没法看屏幕，只能靠 hook 日志观察——把关键数据在 hook 里打出来
（H5 收到的 JSON、定位替换值），用日志代替眼睛。

**教训**：做逆向/调试时，"能观测"比"能操作"更重要，提前把日志埋点设计好。

---

## 15. `/sdcard` 上 chmod 无效

**现象**：`chmod 644 /sdcard/Download/x.json` 执行成功，`ls -l` 还是 `rw-rw----`。

**定位**：`/sdcard` 是 FUSE，权限由上层策略决定，mode 位改不动。

**解法**：别指望用 mode 控制访问；能不能读取决于对方有没有存储权限、是否 scoped storage。

**教训**：共享存储不是普通文件系统。

---

## 16. 别直接改 LSPosed 数据库

**观察**：`/data/adb/lspd/config/modules_config.db` 是 SQLite，能看到 `modules` /
`modules_state` / `scope` 三张表，理论上可以手工插入记录来"启用模块"。

**结论**：**不建议**。lspd 在内存里维护配置，外部改库不会通知它，可能被回写覆盖，
严重时导致 LSPosed 配置损坏。`lspctl` 只有 `status` / `stop`，没有启用命令。

**正确做法**：让用户在 LSPosed 管理器里点两下。

---

## 17. hook 接口方法没效果

**现象**：hook 了 `BDLocationListener.onReceiveLocation`，回调完全没被拦截。

**原因**：接口方法没有实现体，实际执行的是实现类里的方法。

**解法**：hook 调用点（`registerListener(...)` 把参数换成 Proxy），或者 hook 实现类的方法。
本项目最终选了更简单的方式——直接 hook 数据对象（`BDLocation`）的 getter。

**教训**：选 hook 点时，优先选"数据出口"而不是"回调入口"，前者覆盖所有消费方。

---

## 18. 静态方法里 `getThisObject()` 为 null

写 hook 时如果无脑 `chain.getThisObject().xxx()`，遇到静态方法（如
`Build.getSerial()`、`Settings.Secure.getString()`）会直接 NPE，把目标应用搞崩。

**写法**：先判空，拿不到就 `chain.proceed()`。

---

## 19. 多进程重复安装 hook

目标应用有 `:remote` 进程时，`onPackageReady` 每个进程各触发一次。如果 hook 里带状态
（比如"只记录一次"），要注意这是**进程级**的，不是全局的。安装 hook 本身用静态标志防重入即可。

---

## 20. hook 失败要静默降级

所有 `hook(...)` 都包在 `try/catch` 里，失败只打 `Log.WARN` 不抛出去。
否则目标应用可能因为一个可选的 hook 失败而崩溃，用户看到的是"模块把 App 搞坏了"。
