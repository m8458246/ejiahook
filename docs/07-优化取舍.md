# 07 优化取舍（2026-11-11 审查报告落地记录）

审查报告：`optimization-report-20261111.md`（基于提交 `8f63825`）。
本项目的原则：**先保证 hook 行为正确、目标 App 不崩、能覆盖安装**，再谈安全与工程治理。
下面是逐项取舍，以及为什么有些建议明确不采纳。

## 已采纳

| 报告项 | 落地内容 |
|---|---|
| P0-2 调用方约束 | `ConfigProvider.call` 只接受本应用 UID 或 `com.dcits.ehome` 的 UID；广播回传在 API 34+ 校验发送方 UID，并要求请求时间窗内 |
| P0-3 采集跨事件混合 | 采集绑定到单个 `BDLocation` 实例，换对象就重置；被写回过的对象不再当真实值；内容变化才补发（地址后到也能补上） |
| P0-4 静默失败 | `writeConfigFile` 返回真实结果，保存提示区分“共享文件成功 / 仅模块配置 / 写入失败”；Android 10 以下不再误报失败 |
| P1-4 分项容错 | 每个 hook 单独 try/catch 并记录；坐标 getter 额外校验返回类型；`sInstalled` 放在全部安装之后 |
| P1-5 输入校验 | 经纬度必须有限且在范围内，半径 0–5000；用“字段是否填写”判断目标坐标，不再把 `(0,0)` 当哨兵 |
| P1-1 root 检测可控 | 新增「屏蔽 root 检测」开关，**默认开启**（保持原行为，避免目标 App 识别 root 触发风控）；关闭需重启目标 App |
| P2-1 性能 | `Config.signature()` 结果缓存，避免每次 getter 都 `String.format`；`appContext()` 缓存；配置文件优先直读 `config.json`，目录枚举结果缓存 30 秒；`Drift` 缓存满时只淘汰一条，不再整体 `clear()`（否则同一次定位的坐标会抖） |
| P0-3 内存 | 采集对象改用弱引用，不把最后一个 `BDLocation` 长期吊在静态字段里 |

## 明确不采纳

| 报告项 | 不采纳原因 |
|---|---|
| P0-1 轮换发布签名 | 换签名意味着老用户必须卸载重装、模块作用域重配。当前仓库的 keystore 是自用分发链路的一部分，换签名造成的可用性损失大于收益。若将来公开分发，再单独做迁移方案。 |
| P0-2 用 nonce 当认证 | nonce 要经公共配置文件传给目标进程，任何能读该文件的一方都能拿到，不是身份凭据。现有“调用方 UID + 时间窗”已经覆盖真实威胁模型，再叠一层只会增加采集失败的概率。 |
| P0-3 关闭伪造后拒绝写回 | 写回是保证同一 `BDLocation` 上其它读取方也看到伪造值的关键（幂等纠正）。去掉会让地图 SDK、后续 getter 读到真实坐标，属于破坏 hook 完整性。改为“被写回过的对象不参与采集”。 |
| P0-4 配置读不到就停止伪造 | 框架通道偶发失败很常见。一旦读不到就透传真实坐标，用户会在不知情时打卡到真实位置，后果比“沿用上一次有效配置”严重。保留回退，只在日志里标注来源。 |
| P1-2 日志默认关闭 | 定位日志是这个模块自查“到底改没改成功”的主要手段，且只写 300 行、只在本机 Download 目录。关掉会让排障成本大幅上升。 |
| P1-3 坐标系转换 | 目标 App 全链路（百度 SDK → H5）都用 GCJ-02，界面也按 GCJ-02 输入。擅自加 WGS-84 转换会直接让坐标偏移几百米。 |
| P1-6 按标识类型分别校验 | 目标 App 三套取号逻辑最终都落到同一个字符串，强行按 IMEI/MAC 格式分流会让 `android_id` 覆盖失效。只在 MAC 场景做格式判断。 |
| P2-2 拆分 CI / 恢复 lint | 当前 CI 是“push 即出包”的自用链路，拆 job、加门禁会拖慢出包。lint 恢复留到有测试基线之后。 |
| P2-1 日志改追加+轮转 | 现在每次重写 300 行、文件不到 20KB，实测没有可感知开销；改成追加会破坏“新的在最上面”的阅读习惯。 |
